## Использованный промт для генерации данных:

Я прикладываю таблицу/схему базы данных. Ориентируйся строго на неё. Не пересказывай и не переописывай схему заново, а просто извлеки из неё структуру таблиц, полей, типов данных, ключей, внешних ключей и ограничений.

Сделай набор данных похожим на демонстрационный датасет для защиты проекта: он должен быть не минимальным, а показательным, разнообразным и удобным для проверки запросов. Данные должны быть специально подобраны так, чтобы в базе были представлены разные допустимые варианты значений, разные статусы, разные типы объектов и разные случаи связей, а не повторяющиеся шаблонные записи.

Нужно сгенерировать только данные для всех таблиц. Я потом сам загружу их в базу данных своим скриптом. Поэтому не нужно генерировать SQL-скрипт, `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE` или `INSERT INTO`.

Сделай строго следующее:

1. Сгенерируй реалистичные тестовые данные для всех таблиц:
   - не менее 20 строк в каждой таблице, но можно и больше, если это делает данные правдоподобнее;
   - данные должны быть разнообразными, а не однотипными;
   - нужно показать разные реальные сценарии использования базы;
   - все внешние ключи должны быть корректны;
   - все ограничения из схемы должны соблюдаться.

2. Обязательно проиллюстрируй данными все типы связей, которые есть в схеме:
   - 1:1, если они есть;
   - 1:N — обязательно должны быть примеры, где одной записи соответствует несколько связанных записей;
   - M:N — если связь реализована через промежуточную таблицу, заполни её так, чтобы были показаны разные комбинации связей.

3. Сделай данные не однообразными, а намеренно разнообразными:
   - используй разные статусы, типы, классы и другие допустимые значения из схемы;
   - добавь записи с разными сценариями: обычные случаи, пограничные случаи, разные категории объектов;
   - там, где это логично, включи данные с NULL, если это разрешено схемой;
   - значения должны выглядеть как правдоподобные данные предметной области, а не случайный набор строк.

4. Соблюдай логическую согласованность данных:
   - значения времени, дат, статусов и зависимых сущностей должны быть согласованы между собой;
   - родительские записи должны существовать раньше дочерних;
   - связанные данные должны соответствовать смыслу предметной области;
   - не создавай формально валидные, но нелогичные записи.

5. Выведи результат только в виде CSV-данных для всех таблиц:
   - отдельный CSV-блок для каждой таблицы;
   - в каждом CSV первая строка — заголовки;
   - назови каждый блок как имя файла, например `flight.csv`, `booking.csv` и т.д.;
   - не добавляй SQL вокруг CSV;
   - не используй markdown-таблицы, только чистый CSV-текст.

6. В конце сделай краткую самопроверку:
   - сколько строк сгенерировано в каждой таблице;
   - какие связи проиллюстрированы данными;
   - какие группы ограничений были соблюдены.

Важно:
- PostgreSQL.
- Ориентируйся только на приложенную таблицу/схему.
- Ничего не переименовывай и не придумывай новые столбцы, которых нет в схеме.
- Не пиши объяснений вместо результата.
- Сначала внимательно извлеки структуру из приложения, затем построй данные строго по ней.
- В ответе не должно быть `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE`, `INSERT INTO` и любых SQL-команд — только данные таблиц в CSV.
